# Contact velocity preview

SARDAB can estimate attack velocity from the FM-1's key contacts, using the
GPIO/ADC technique from [fm1-velocity](https://github.com/charlesvestal/fm1-velocity/tree/8f62ce0d968c91ce8bfdafbb908f81d15351650a).
It needs no hardware modification. This port has passed host and target-build
checks; its response and latency still need validation on a physical FM-1.

## Enable it

1. Hold **HOME** to open MENU, then **release HOME** before editing.
2. Turn **ALGORITHM** to the **TOUCH** tab.
3. Turn **PRESETS** to **VELOCITY**; turn any numbered knob clockwise (or press
   **OCT+**) to select **SENSE**. Counterclockwise / **OCT−** selects **FIXED**.
4. Start with **CURVE LINEAR**, **TOUCH NORMAL**, **TOP KEYS PROBE**.
5. Press **HOME** to close the menu and save the settings.

| Setting | Effect |
| --- | --- |
| VELOCITY FIXED | Original keyboard behavior, using the SELECT VEL performance value (initially 100). Default for existing settings. |
| VELOCITY SENSE | Each physical key gets an attack velocity from 1 to 127. |
| CURVE LINEAR / SOFT / HARD | Straight response; SOFT raises intermediate velocities; HARD lowers them. |
| TOUCH NORMAL / LIGHT / FIRM | Manual sensitivity. LIGHT reaches strong velocities with lighter contact; FIRM requires stronger contact. |
| TOP KEYS PROBE / FIXED | Sense the seven upper keys through the indirect probe, or use the fixed performance velocity for those keys. |

These are global settings and travel in complete backups. Project and user
preset formats are unchanged. The hardware menu is also visible in the emulator,
but mouse/computer-keyboard presses cannot simulate contact resistance and use
fixed velocity. External MIDI retains its incoming velocity.

## Chords, maqam and recording

One physical attack supplies the velocity for all notes generated by its chord,
including the layered track. Pitch mapping, maqam offsets and tuning remain
independent. Engines receive velocity as before; how audible it is depends on
the preset and its modulation assignments.

Live recording stores the velocity and sequence playback uses it. **Each step
has one shared velocity:** if several notes are recorded into a step, the
strongest attack wins. This does not store a separate velocity for each note
of a polyphonic step. An explicit step accent still overrides velocity to 127.

The arpeggiator now keeps the input velocity attached to each held note through
sorting, octave expansion, REPEAT, TRILL, CHORD and DRONE, including MIDI input.
Previously it forced its generated notes to 100. Recording its output preserves
those velocities subject to the same shared-step rule. With the usual fixed
keyboard velocity of 100, its behavior is unchanged.

## What to check on your device

Use a velocity-responsive preset and try soft, medium and firm attacks across
all keys, especially the seven upper keys. Try fast repeated notes and chords.
Record a short phrase and compare playback dynamics. A MIDI monitor can show
the velocities sent by live physical keys, making response easier to judge.

The twenty directly sensed keys and seven indirectly probed keys use different
response ranges. Finger placement and contact condition affect the estimate;
this is not a two-contact keyboard mechanism. There is no adaptive calibration
or aftertouch in this port. If the upper keys respond poorly, select TOP KEYS
FIXED. Return VELOCITY to FIXED to disable sensing entirely.

SENSE delays the beginning of a note while sampling. If no valid capture arrives
within 14 ms of the audio path observing the press, it uses the fixed velocity.
This is a timeout, not a measurement of total key-to-audio latency. Release
continues to use the digital key scan; a key released while waiting cannot
produce a delayed note. Changing response settings never retriggers a held key.

## Validation and integration

Tests cover simultaneous captures on all 27 keys, fast repeats, release while
waiting, timeouts, mode changes, manual curves, top-key fallback, maqam chords,
layers, MIDI, recording/playback and every arp mode. HAL tests check ADC
ownership and GPIO restoration on success, timeout and disabling sensing.
Address/undefined-behavior sanitizers, target size/instruction checks and
emulator audio comparisons supplement these tests; they do not measure the
physical contacts or hardware interrupt timing.

The scheduler owns ADC conversions after boot, including MASTER and battery.
Driven pins are restored before digital scanning; conversions never busy-wait
inside the input interrupt. The source attribution is in [LICENSING.md](../LICENSING.md).
